What happens during an install

#What happens during an install

From power-on to Ready, in order. The middle column is what the boot server's window (and %LOCALAPPDATA%\stolos\boot\boot.log) shows; the last column is where to look when a step fails.

| # | Step | Boot server shows | Where to look | | -- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- | | 1 | The firmware asks DHCP for an address and the network boot server (your router answers: next-server = the PC, boot file bootx64.efi) | nothing yet | the server's screen; your router's DHCP settings | | 2 | Firmware downloads Ubuntu's signed shim over TFTP; shim downloads Ubuntu's network GRUB (Secure Boot checks both) | TFTP bootx64.efi, TFTP grubx64.efi | boot server window; firewall (UDP 69) | | 3 | GRUB asks for its menu; the boot server recognizes the machine (Boot URI, claim, or learned MAC) | claimed by alpha or alpha: armed, starting its install | bun run stolos boot status | | 4 | GRUB downloads the kernel and installer initrd (about 120 MB) over TFTP | TFTP linux, TFTP initrd | boot server window | | 5 | The installer boots and downloads the Ubuntu image (2.9 GB) over HTTP | installer image (whole) | the server's screen; firewall (TCP 8080); the boot server warns after 3 minutes if HTTP never arrives | | 6 | The installer fetches alpha' install config; the boot server fills in the secrets (password hash, deploy key, SSH host keys, mail token) | install config sent (network on <mac>) with its ... | boot server window | | 7 | Unattended install: disk, Ubuntu, kernel, updates, configuration | installer: partitioning the disk, copying Ubuntu to the disk, installing the kernel, installing updates, configuring the installed system; any failed step as ✗ installer: ... | on the host afterwards: /var/log/installer/ | | 8 | The installer records the network boot entry, reports done, and reboots | install finished; disarmed, this PC trusts its SSH host keys for ... | boot server window | | 9 | First boot (cloud-init): installs the pinned Bun, clones the repository with the deploy key, installs the engine bun.lock holds | First boot: installing Bun, cloning the repository | on the host: /var/log/archon-first-boot.log | | 10 | archon first-boot: apply (packages and PPAs, accounts, files, units), mail token, GitHub, tools, dotfiles, verify, record | one line per phase, for example ✓ Tools: ..., ✓ Verify: 44 passed | on the host: /var/log/archon/<time>.log (the run log), /var/log/archon-first-boot.log | | 11 | The first record is pushed to GitHub (archon.sql alpha/installed.json) | ✓ Ready: 44/44 checks · ssh alpha, or ✗ Done with problems: ... | installed.json (ok, problems) |

Timing on real hardware: steps 1 to 6 take a minute or two (mostly the image download), the install itself a few minutes, the first boot a minute or two.

After Ready, the host converges to GitHub every 15 minutes by itself (archon-reconcile), and ssh alpha connects without questions.

#Modules

apt-busySpec 054: powering a machine off while apt or dpkg runs can break dpkg's state (the lab did it: dpkg's files were left empty).
bunThe pinned Bun (spec 096-bun-runtime FR-007): the runtime every host, the boot server and the operator's PC run the engine with, and how a fleet checkout gets its engine.
first-bootarchon first-boot (spec 005): run once by cloud-init on a freshly installed host, after the first-boot script cloned the repository with this host's deploy key.
host-addstolos host add (spec 004): write the host's model, give it its own GitHub deploy key (read-only access to this repository (spec 048); the private half stays in the boot machine's secret store),…
host-bootstrapstolos host bootstrap (spec 005): finish a host whose Ubuntu was installed by hand (from Ubuntu's ISO, a cloud image, anything) instead of by network boot.
host-keysEach host's SSH identity (spec 004): its host keys are made once on the boot machine (ssh-keygen, as for the deploy key), kept in the secret store, and installed by cloud-init at every install.
netbootarchon reboot [--netboot] (spec 004): for a re-install, boot from the network once (UEFI BootNext) and then reboot.
publishSpecs 004 and 045: what stolos host add and boot retire change in the checkout is built, committed, and pushed by the same command (pushing to main is approval, Article 9).
recognizeSpec 051: how a machine becomes a host when it network-boots.
reportFirst-boot progress to the boot server's window (spec 004): the install left the URL in /etc/archon/boot-events.
runnableSpec 063: before a machine is armed, check that what it will run is there.
re-exportsWhat What happens during an install exports from elsewhere, so that its users need import nothing else.
ubuntuThe Ubuntu point release hosts are installed from (spec 004 pins).
workstationstolos workstation add (spec 020): run inside Ubuntu on WSL (or on an Ubuntu desktop), from the checkout in /srv/archon, as your own user.
