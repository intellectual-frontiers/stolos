review

Spec 080: review through signed pull requests. A review changes a file in the fleet repository (a risk's next review date in risks.ts; new vendors in vendors.ts) on a branch of its own, in a commit signed with the reviewer's daily key, and opens a pull request with gh. The approval is the merge: a merge commit on the fleet's main branch signed by a fleet signer (git merge --no-ff -S, then stolos apply), checked like spec 072's evidence: git verify-commit against the fleet's signers.ts. A merge made on GitHub's website is signed by GitHub, not by a signer: it is approved by the next signed commit on main (stolos apply makes one), and approvalOf says which.

Source: src/archon/risk/review.ts

Approvalinterface
interface Approval

Who approved the last change to a file: the commit, and the fleet signer who signed it (or a later one).

MemberTypeWhat it is
commit?stringThe commit on the main line that last changed the file (a merge commit, for a merged pull request).
signer?stringThe fleet signer who signed it.
approvedBy?{ commit: string; signer: string; }A later signed commit on the main line that approved it, when the change itself is not signed.
reason?stringWhy it is not approved.
approvalOffunction
function approvalOf(repo: string, path: string, allowedSigners: string): Promise<Approval>

The approval of the last change to path: the first-parent commit that changed it (the merge commit of a merged pull request), checked with git verify-commit against allowedSigners (the fleet's signers.ts as Git's allowed_signers). An unsigned one is approved by the first later signed commit on the main line, as servers do (spec 060).

openReviewfunction

Open a review: from a clean checkout, a branch from the base on GitHub, the edit, one signed commit, a push of that branch, and a pull request (gh pr create); then back to the branch it started on. Nothing is merged: a signer approves by merging.
