Remote access to the Stolos Console

#Remote access to the Stolos Console

bun run stolos console answers on 127.0.0.1 only. bun run stolos console --lan (or stolos: { console: { lan: true } } in fleet.ts) also serves it over HTTPS on this PC's LAN address, so a phone or a laptop on the site's network can open it (spec 100):

AddressWhat
https://stolos.lab.example.netthe primary controller
https://alpha-pc.stolos.lab.example.netone controller by its name (<pc>.stolos)

The first time, it proposes the names under the fleet's web.domain and writes them into fleet.ts (send them: bun run stolos apply). It keeps their A records in Cloudflare (this PC's LAN address, not proxied), with the token of bun run stolos boot web-setup, and gets a Let's Encrypt certificate through the DNS challenge, kept in the vault (console/tls.json, in every backup) and renewed 30 days before it expires. It never listens on a public address (Article 28): from outside the LAN, use a zero trust mesh network (bun run stolos mesh).

#Port 443 only

The console's LAN listener is TCP 443, one of the three ports this PC opens (constitution Article 29: UDP 69 and TCP 8080 for the boot server, TCP 443 here), and the only port it tries: there is no fallback. If 443 is in use or not allowed, console --lan refuses to listen and says what holds the port (Windows: Get-NetTCPConnection -LocalPort 443 -State Listen; Linux: ss -ltnp; macOS: lsof -iTCP:443 -sTCP:LISTEN) and the fix; boot doctor reports the same. bun run stolos console --lan --lan-port <n> is the explicit choice of another port: it says it is outside the three standard ports and prints its own firewall rule. On these names the console also serves pairing at /device/pair (door B, spec 098 and 103-three-ports): no session or passkey, only while a pairing waits, and never on the 127.0.0.1 listener.

#Signing in from a device

There is no password. A device makes a passkey, and a fleet signer approves it with a signed commit, as every other decision:

  1. Open https://stolos.lab.example.net, choose Register this device: pick your signer name, name the device, and let the browser create the passkey. The page shows a code.
  2. A signer approves it: on the controller's Remote Access page (Approve; the passphrase is asked on the page), or on their own PC: bun run stolos devices approve WDJB-MJHT --controller https://stolos.lab.example.net. Either writes the device into fleets/<fleet>/access.ts and sends it with stolos apply, signed by their key.
  3. Once the controller reads that signed commit from GitHub, the waiting page offers Sign in with your passkey.

#Who may do what

A signer whose key is on the controller (its daily key, or a recovery key in its vault) may run every command the console offers. Every other signer looks: each page, and the read-only commands; a command that changes the repository answers with the line to run on their own PC.

#Keeping it reviewed

WhereWhat
Remote Access pagenames, certificate, every device and its last sign-in, codes, refusals
bun run stolos devicesthe devices (access.ts) and their last sign-in here
bun run stolos devices revoke <id>remove one (signed); refused once the controller reads it
the fleet's mailboxeach registration, approval, denial, revoke, five failed sign-ins; a daily digest
bun run stolos boot doctorthe listener, the certificate's expiry, devices unused for 90 days, the firewall

access.ts is a decision, not a record: stolos update never sends it by itself (the commands that change it send it at once, signed by whoever decided).
