Adopted machines

Stolos manages the servers it installs. Every other machine you are responsible for (your laptop, a colleague's desktop, a WSL distribution, a server someone else installed) can be adopted: Stolos observes it and checks it, and never changes it (spec 067).

  pc["Your PC: bun run stolos"] -- "probe key (vault)" --> sshd["sshd on the machine"]
  sshd -- "forced command" --> probe["~/.local/bin/stolos-probe: read-only"]
  probe -- "facts" --> pc
  pc -- "observed.ts" --> git["Fleet repository"]

The easy way: one line on the machine

In the Stolos Console, Add a machine asks what it is (a laptop, a device, a cloud account, a server to manage, a workstation) and gives you one line to run on it, or to send to its owner. The same from the command line:

bun run stolos host integrate alice-laptop --as adopt

On the machine, the line (bin/integrate.sh on Linux and macOS, bin/integrate.windows.ps1 on Windows) lists every change it will make and asks once. It ends by printing a check-in code (stolos1:...): paste it into the console, or:

bun run stolos host adopt alice-laptop --check-in stolos1:...

The code carries the machine's public SSH keys, so they are pinned without trusting the first connection. --as discover changes nothing on the machine: discover --import <code> records it.

Windows is adopted the same way: the line turns on Windows' own OpenSSH Server and installs a PowerShell probe (BitLocker, Windows Firewall, Windows Update, Defender, Administrators).

Devices

Printers, routers, switches, access points, NAS boxes, cameras, and UPSes are read over SNMPv3, encrypted and read only (Stolos sends only GET and GETNEXT; never SNMPv1 or v2c). Make a read-only SNMPv3 user on the device (authPriv, SHA-256, AES), then:

bun run stolos device add front-printer --address 10.0.30.40 --kind printer --user stolos

Its passphrases are typed in the terminal and kept in the vault; its model, serial, firmware, uptime, contact, and location go to fleets/<fleet>/devices/front-printer/observed.ts. device check reports its policies (observed, an owner and location, restarted for firmware).

Adopt a machine over your own SSH

bun run stolos host adopt alice-mbp --ssh alice@alice-mbp.local --owner alice

It shows the machine's host key (compare it with ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub on the machine), makes a probe key in the vault, installs the probe over your own SSH (it may ask your password once), and records what it found.

The probe key can do one thing: run the probe. Its line in ~/.ssh/authorized_keys forces the command and forbids a shell, a terminal, and forwarding. The probe needs no root and listens on nothing.

When a policy cannot pass

Sometimes a policy cannot pass, for a good reason: a Linux desktop installed without disk encryption that holds no customer data, say. Record that decision instead of living with a red line:

bun run stolos host accept bob-desk disk-encryption --reason "holds only open-source code; no customer data" --until 2027-06-30

The policy then shows as accepted (not as passing), with who accepted it, why, and until when; Compliance counts it as partial. After the date it fails again, so the decision is reviewed at least yearly. The signed commit that keeps it is the auditor's record.

Discovered machines

bun run stolos discover lists the machines this PC has seen on its network (its neighbor table) and the cloud servers no fleet machine owns. It scans nothing and records nothing; adopt the ones you are responsible for.

The policies

Each policy names the Secure Controls Framework (SCF) controls it gives evidence for: the disk is encrypted (CRY-07), the firewall is on (END-07, NET-02), security updates install by themselves (VPM-08), the OS is supported (AST-39), SSH takes keys only (IAC-14), at most three administrators (IAC-30), observed in the last week (AST-04, MON-02). The frameworks are reached from those through the SCF Council's own mappings (see Compliance).

Cloud accounts

Stolos can also see what the fleet keeps in its clouds, read-only: it never creates, changes, or deletes anything there (managing a cloud stays in that cloud's own console).

A laptop the probe adopted, Intune manages, and Falcon protects is one device in the estate: the graph merges every source's devices by serial number, then hostname, and records which source each property came from (the probe first, then the MDM, then the EDR).

bun run stolos connect github

connect shows how to make a read-only credential in the provider's console, asks for it here (nothing you type is shown), keeps it in the vault, and observes once. Then:

  • bun run stolos estate observe reads every connected account again (daily is plenty);
  • bun run stolos estate check reports the posture (--json for an auditor);
  • bun run stolos estate assets --kind dns-record lists every DNS record and the machine it points at;
  • git log -p fleets/<fleet>/estate/cloudflare.ts shows what changed, and when;
  • bun run stolos disconnect cloudflare forgets the credential (revoke it in Cloudflare too).

A part the credential may not read (Workers, say) is listed as not readable, not as a failure.

Open vulnerabilities (Snyk, Tenable, Dependabot) are OCSF Vulnerability Findings: each open one is an item of the OSCAL plan of action and milestones, with its CVE, severity, and asset. Training completions (KnowBe4) and screening outcomes (Checkr) are the records the people controls read beside people/training.ts and people/screening.ts. A connector Stolos does not ship can be added from its own repository, pinned and locked like the engine: see the connector registry.

Every connector is labeled the way the industry labels it: its NIST SP 800-145 service models (IaaS, PaaS, SaaS) and its market categories as the analyst firms name them (Strategic Cloud Platform Services, Access Management, DevOps Platforms, Cloud HCM Suites, ...).

Across systems: the estate graph

People, accounts, machines, and repositories meet in one graph (spec 090). People come only from the source of truth (the HR system; with none, the identity provider), and every other system's accounts link to them by work email. Machines are deduplicated by serial number, then hostname. bun run stolos estate check reports what no single system can say (people who left with accounts still on, accounts no person owns, administrators without a second factor, people without a machine), and one SQL question spans them all:

bun run stolos estate query "select connector, display_name from user_account where admin = 1 and mfa = 0"
bun run stolos estate diff "select uid, hostname from device" --since 2026-10-01
bun run stolos estate build
bun run stolos estate schema --docs

The tables follow the Universal Data Model (person, party_role, contact_mechanism, fixed_asset, ...) and a property graph (tenant, node, edge); views carry OCSF's and D3FEND's names (user_account, code_repository, user_inventory, device, compliance_finding). First seen and last seen come from Git. estate build writes the graph as canonical SQL (estate.sql, loadable into other databases) and as estate.auto.sqlite.db.

The estate graph in osquery

estate build also writes estate.osquery.json (spec 093): an osquery configuration that makes every estate table and view an osquery table named stolos_<name>, through osquery's Automatic Table Construction (osquery reads the SQLite file itself; no extension runs). It is generated from the schema's declarations, so each table has exactly the declared columns. On your PC, where the file is, osquery can join the estate with what it sees on the machine:

bun run stolos estate osquery          # write the configuration; print its path and how to load it
osqueryi --config_path <that path> "select uid, hostname, owner_email_addr from stolos_device"

  git["observations in Git"] --> build["bun run stolos estate build"]
  build --> sql["estate.sql (canonical)"] --> db["estate.auto.sqlite.db"]
  build --> conf["estate.osquery.json"]
  conf --> osq["osqueryi or osqueryd"]
  db --> osq --> t["stolos_device, stolos_user_account, ..."]

For an osqueryd that already has a configuration, or a fleet manager, merge the file's auto_table_construction object into the configuration it uses (estate osquery --print prints it). Every column is text in osquery, and each table has osquery's own path column.

A system that knows people by login only (GitHub) is linked to work emails in fleets/<fleet>/estate/links.ts: export const links = { "github:alice": "alice@example.org" };. A machine two sources see under different names is joined there too: "device:snmp:printer": "hostname:front-printer".
