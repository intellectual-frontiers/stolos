Stolos

Stolos, the fleet engine: the archon command, the boot server, and everything general about turning bare metal into a converged, verified Ubuntu host. A fleet repository depends on it by Git at a tag (spec 096-bun-runtime). Start with the guides: each is the overview of the area of the code it explains (spec 070-docs-in-code).

#Capabilities

Each capability is a specification of the engine's spec kit, under the one it is part of.

Platform (Ubuntu Server 26.04 LTS defaults)001Record which Ubuntu Server 26.04 LTS defaults Archon relies on, verify them on every host, and list every override with its reason (Articles 1 and 2).
Model, validation, rendering, export002The fleet and its hosts are TypeScript; TypeScript validates them; Archon renders every native format from them; RDF is an export (Articles 4, 7, 10).
Fleet identity and secrets003The primary user's name, ID, keys, and commit address come from GitHub through gh; secrets stay on the boot machine (Articles 13, 17).
Boot and install (UEFI HTTP Boot, autoinstall)004A host is created from its model by PXE (TFTP) or UEFI HTTP Boot served by archon-boot on the boot machine (Windows or Linux) and Ubuntu's unattended installer (Article 18).
First boot005On its first boot a host clones the repository with its deploy key, converges, verifies, and pushes its first record.
Accounts and personas006The fleet admin and ops on every host, Archon's persona groups, and the operator sudo rule.
SSH007SSH keys from anywhere; passwords as well from local networks (owner's decision, 2026-11-11).
Firewall008Ubuntu's native firewall (ufw on nftables), incoming denied except modeled ports.
Updates009Ubuntu's unattended-upgrades as Ubuntu configures it, also installing Ubuntu's stable updates daily (owner's decision, 2026-11-10).
Tools010The developer and operator tools at their newest stable release: the maintainers' PPA when they publish one, else the upstream binary release, else Ubuntu's archive (Article 5).
Shell environment011Persona-driven dotfiles through chezmoi: fish with oh-my-posh (the Archon status segment), tmux, git identity.
CLI and MCP012One command registry yields the CLI, MCP tools, man pages, completions, and the agent's permissions (Article 6).
Ops reports013Each server writes and mails a deterministic daily health report.
State, provenance, and push014Every host records what it is and what was done to it, in the repository, exportable as RDF (Articles 15, 16).
Update and reconcile015Hosts converge to the repository (Article 9), on a timer and on demand.
Backups016Anything that holds state is backed up and restore-tested (Article 14).
Guests (LXD)017Containers and VMs with Ubuntu's native manager, LXD (a snap; lxd-installer is preinstalled).
Out-of-band management018Console access when the network or the OS is down: Intel AMT on the Minisforum MS-01 (the i226-LM port).
Operator output019Calm output for every operation (Article 19).
Workstation (Ubuntu on WSL)020The owner's Windows PC runs Ubuntu on WSL; it should get the same tools, dotfiles, prompt as the hosts, managed by Archon, without anything that belongs to a server.
Local observability, OpenTelemetry as the protocol021Make every server and workstation observable.
Cockpit022A local web view of each server, Ubuntu's own: Cockpit, with the metric history spec 021 keeps, reachable from the local networks only.
Boot server telemetry023The boot server observable with OpenTelemetry, its files kept on the boot machine.
Finding a central collector024A central OpenTelemetry collector will run later, on the boot machine or a container host.
Notifications by email025Major events on every server, workstation, and the boot machine should reach the owner without anyone watching a terminal: email to the shared mailbox fleet@example.net, from root+<host>.lab@example.net.
