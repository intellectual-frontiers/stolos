The auditor portal

#The auditor portal

An external auditor tests a control by sampling its population and examining each sample's evidence. Stolos gives them both from the signed evidence bundle (spec 072), so they verify each sample themselves and never need a screenshot (spec 083).

#1. Open an engagement

The engagement is fleets/<fleet>/audits/<id>/engagement.ts: the firm and its people, the period, the frameworks, the controls in scope (each with the population it is tested on), the evidence bundle (pinned by its SHA-256), and the last day of the auditor's access. Each audit command makes one commit of the engagement's files, signed with your daily key; push it as any change (stolos apply). audit access moves the last day; audit close ends the engagement.

#2. Populations

Each control is tested on a population computed from the pinned bundle, never from this PC's live state, so the auditor gets the same units and the same population hash from the bundle alone:

PopulationOne unit is
changea commit to the fleet repository in the period
leaversa person whose employment ended in the period
mfaan active account (not a service account)
devicesa device, or a machine Stolos adopted
repositoriesa code repository
access-reviewsa manager's quarterly access review
verifya managed server's verify or install result

Each unit names the bundle items that are its evidence, by SHA-256.

#3. Samples

The auditor chooses the sample size (by their firm's methodology) and gives a seed: any text, such as a number they picked or a public randomness beacon's value they chose. Stolos draws by simple random sampling without replacement with random sort keys (each unit's key is sha256(seed + newline + unit id); the sample is the units with the smallest keys), so the auditor redraws it with a shell:

The sample, the seed, the method, and the population's hash are recorded in the trail.

#4. Requests and responses

Each is a numbered file in audits/<id>/trail/, added in a signed commit whose trailer names the file's SHA-256: the signature covers the exact text. The portal shows them in order, each with its commit and signer.

#5. The portal

It starts the Stolos Console on 127.0.0.1 and prints a link that works once, for two minutes, and opens a session that sees only this engagement, read-only, for at most four hours. Every page refuses once the engagement has expired or been closed. The auditor sees each control's population, each sample's evidence items with their SHA-256 and place in the signed manifest, and verifyBundle's result, and downloads any item or the whole bundle. The same data is JSON under /v1/audit/<id>/ (in the console's OpenAPI document).

#6. A remote auditor: the export package

The console answers only on this PC. For an auditor elsewhere, send the export package:

It holds the bundle, engagement.ts and every trail entry with the raw signed commit that recorded it, the populations, the fleet's signers, and the portal as one static page. audit verify checks the bundle, every commit's trailer and signature, and recomputes every population and redraws every sample; its README says how to do the same by hand. The package is not time-boxed: sending it is your decision.

#Modules

engagementSpec 083: an audit engagement, as a file in the fleet repository: fleets/<fleet>/audits/<id>/engagement.ts.
populationsSpec 083: populations.
sampleSpec 083: samples, drawn so the auditor can draw them again.
trailSpec 083: the audit trail.
caseSpec 083: one engagement, read and checked: its file and the commit that vouches for it, its evidence bundle (verified with verifyBundle), the population of each control in scope, the trail with…
commandsSpec 083: stolos audit ....
openapiSpec 083: the auditor portal's JSON routes in the console's OpenAPI document (GET /v1/openapi.json), under /v1/audit/{engagement}/.
packageSpec 083: the export package, for an auditor who works remotely or offline.
portalSpec 083: the auditor portal, served by the Stolos Console on 127.0.0.1.
