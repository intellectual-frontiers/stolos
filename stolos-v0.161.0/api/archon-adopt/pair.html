pair

Specs 098 and 107-pairing-and-query: pairing with a short code. The way a person brings machines into the fleet without copying a key or a hash by hand, modeled on device login: the controller PC shows one short, fixed command and a code; the person runs the command on each machine and types the code; the PC shows who asked, one machine after another, and the person approves each there. One session pairs many machines, at the same time or one after another, and stays open until the person who started it stops it.

This module is the protocol, with no network or terminal of its own: PairSession answers the machine's HTTP requests, with its state in a PairStore (spec 103-three-ports), so that every door (the boot server's HTTP, the console's TLS, or the pair-only server stolos pair runs) mounts the same handler over one record, and stolos pair (in pair-command.ts) asks the person.

Every route lives under /device/pair (the ontology's device path, spec 103-three-ports FR-003), here written relative to that base:

RequestWhat it is
GET <base>the POSIX script: bin/integrate.sh, from this engine, with the pairing filled in
GET <base>/wa Windows loader: saves <base>/w.ps1 and runs it in a child PowerShell (so a stop never closes the person's window)
GET <base>/w.ps1bin/integrate.windows.ps1, from this engine
GET <base>/bin/stolos-probe.sh, <base>/bin/stolos-probe.ps1the probes, from this engine
POST <base>/hellononce=, hostname= and os= (posix or windows) lines, signed with the code: the answer is the machine's name and the fleet's probe key, signed back
POST <base>/checkinthe check-in text (the same as a stolos1: code, unencoded), signed with the code: the answer waits for the person's decision

While no session is open, every one of them answers 404. Every other answer is 200 with its first line ok or no <reason>, so the smallest HTTP client (a POSIX shell's curl or wget, PowerShell 5.1) reads it the same way. A signature is HMAC-SHA256 under the code (normalized: uppercase, no separators), in lowercase hex, sent in the X-Stolos-Mac header; the PC's answer to hello is signed over nonce, key, name and sha256 (the probe's, for the machine's OS), one per line, so the machine knows the key came from the PC that showed the code and installs only the probe that PC means.

The code is 8 characters from an alphabet without look-alikes (about 39 bits), the same for every machine of the session, and it never expires: the session ends when the person closes it. Wrong signatures are counted per client address (in the store, so by every door and every process together): after 5 that address is refused for the rest of the session, and other addresses are not affected (spec 107-pairing-and-query FR-004). Plain HTTP on the boot server's port is deliberate (the network trust position in the networks guide): on a trusted LAN, or over a zero trust mesh network (Tailscale, NetBird, ZeroTier, Nebula, WireGuard, or similar: see mesh.ts) for anything else, never exposed to the internet; the console's TLS door adds a certificate where the fleet has one.

Source: src/archon/adopt/pair.ts

PairSessionclass
class PairSession

The session's answers, for any door. It holds no state of its own: every request reads the store, so each door and each process that mounts one over the same store serves the same session, counts wrong signatures per address together, keeps every machine that said hello, and holds a machine's check-in until whoever has the terminal (stolos pair) decides on it.
