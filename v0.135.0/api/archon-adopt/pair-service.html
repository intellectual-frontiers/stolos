pair-service

Spec 103-three-ports: what a door mounts to serve the pairing on this PC. The doors (the boot server's HTTP on 8080, the console's TLS on 443, and the pair-only server stolos pair runs when boot serve is not) are different processes from stolos pair; each answers /device/pair from the pairing's file in the secrets folder (SECRETS.pairing) with devicePairHandler, so all of them serve one pairing and count its wrong tries together. The machine is named here (the record's --name, else its hostname's first label; a managed server's name or a bad name is refused) and its probe key made here, in whichever process the machine reached.

Source: src/archon/adopt/pair-service.ts

pairNameForfunction
function pairNameFor(hostname: string, record: Pick<PairRecord, "fleet" | "name">, managed: () => Promise<ReadonlySet<string>>, keyFor?: (name: string, fleet: string) => Promise<string>): Promise<{ name: string; key: string; } | { refuse: string; }>

The name for a machine and its probe key (made now, kept in the secrets folder), or why it cannot have one: the record's --name wins over the hostname; a managed server's name and anything that is not a DNS label are refused with what to type on the PC.

devicePairHandlerfunction
function devicePairHandler(store?: PairStore, o?: { nameFor?: ((hostname: string, record: PairRecord) => Promise<{ name: string; key: string; } | { refuse: string; }>) | undefined; pollMs?: number | undefined; now?: (() => number) | undefined; }): (req: Request) => Promise<Response | undefined>

A request handler for pairing's routes over a store (the pairing's file by default): the answer for a /device/pair request, or undefined for any other path, so a door can try it first and serve the rest itself. With no pairing waiting it answers 404.
