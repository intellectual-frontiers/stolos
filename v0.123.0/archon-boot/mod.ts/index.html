The boot machine

The boot machine is your Windows PC (a Linux PC works too). It holds the fleet's secrets, serves installs, and is where you add and re-install hosts. Nothing on it needs to run except while a host installs.

Install the tools (once)

In PowerShell:

winget install --id Oven-sh.Bun
winget install --id Git.Git
winget install --id GitHub.cli

Open a new PowerShell window (so the new commands are on PATH), then:

gh auth login --web --git-protocol https
git clone https://github.com/example/fleet.git C:\archon
cd C:\archon

Uninstall (or stop) Tftpd64 if you used it before: the boot server is its own TFTP server and needs UDP port 69. netboot.xyz is not needed either.

Allow the boot server through the firewall (once)

Servers reach this PC on TCP 8080 (HTTP: the installer image, each host's config, progress) and UDP 69 (TFTP: PXE). In PowerShell as Administrator:

New-NetFirewallRule -DisplayName "Archon boot (HTTP)" -Direction Inbound -Protocol TCP -LocalPort 8080 -Profile Any -Action Allow
New-NetFirewallRule -DisplayName "Archon boot (TFTP)" -Direction Inbound -Protocol UDP -LocalPort 69 -Profile Any -Action Allow

If Windows once asked whether to allow Bun on public networks and you declined, it added a rule that blocks Bun and overrides these. Remove it:

Get-NetFirewallRule -Direction Inbound -Action Block | Where-Object { ($_ | Get-NetFirewallApplicationFilter).Program -like "*bun*" } | Remove-NetFirewallRule

boot serve and boot doctor check all of this and print the exact command when something would block a server.

Give this PC a fixed address (once)

Your router points network boots at this PC, so its address must not change. In UniFi: Client Devices → this PC → Settings → Fixed IP Address.

Point network boots at this PC (UniFi)

Servers network-boot with PXE: the router's DHCP tells them which server to ask (next-server) and which file to load (boot file). In the UniFi Network app (web or mobile):

  1. Settings → Networks, and open the network the servers get their addresses from (each network or VLAN has its own DHCP settings).
  2. If the DHCP settings are hidden, turn off Auto-Scale Network (the subnet stays as it is).
  3. Under DHCP Service Management (the advanced, _Manual_, section), turn on Network Boot:
  • Server: this PC's address, for example 10.0.1.157
  • Filename: bootx64.efi
  1. Apply Changes.

UniFi sends these as DHCP options 66 and 67. Ordinary devices ignore them, and a machine only network-boots when its firmware is told to, so this is safe to leave on. The labels can move between UniFi Network versions: look for _Network Boot_ in the network's DHCP settings. Replace any old value (a netboot.xyz file name, for example); the boot server serves Ubuntu's boot loader anyway and logs serving bootx64.efi instead.

Servers in a different zone from this PC (for example the Servers VLAN, 10.0.30.0/24, in its own zone and this PC on Default, 10.0.1.0/24) can't reach it until the router allows it: UniFi's zone-based firewall with custom zones blocks connections from the servers' zone into Default. Add two allow policies from the servers' zone to this PC's address, IPv4:

PolicyProtocolPortFor
Servers to boot machine, TFTPUDP69the boot loader, GRUB, kernel, installer (PXE)
Servers to boot machine, HTTPTCP8080the installer image, each host's config, install progress

Without the TCP 8080 policy the network boot gets through TFTP but the installer stops at (initramfs) with wget: can't connect to remote host ... Connection timed out (troubleshooting).

Another router: set _next-server_ (option 66, _TFTP server_) to this PC and the _boot file name_ (option 67) to bootx64.efi.

Describe your fleet (once)

bun run stolos fleet init
git add -A; git commit -m "003-identity: fleet init"; git push

fleet init reads your GitHub identity with gh (login, ID, name, noreply commit address, public SSH keys), asks for your Unix account name and an admin password (typed twice, shown as *; only its hash is kept, on this PC), and writes fleets/<fleet>/fleet.ts. If your GitHub account has no SSH key, it offers to use this PC's key (or create one) and add it to GitHub with gh. It also sets this checkout's git name and address to your GitHub name and noreply address.

The agent (optional)

No agent runs on the servers (spec 030). To manage them with Claude Code, run it on this PC in the checkout; it reaches each server through MCP over SSH. See agent.md.

HTTPS certificates (once, recommended)

Every server answers HTTPS as <host>.lab.example.net with a Let's Encrypt certificate, through Cloudflare's DNS challenge (spec 032). Create a Cloudflare token with Zone > DNS > Edit and Zone > Zone > Read on example.net, then bun run stolos boot web-setup. Servers get it at install, or now with bun run stolos boot web-push <host>. See web.md.

Email (once, recommended)

Every server sends mail through Cloudflare Email Service (spec 027): archon's own notifications (what is sent) and anything a program on it sends (cron, apps, unattended-upgrades). Messages come from <user>+<host>.lab@example.net (for example root+alpha.lab@example.net, or alice+bootpc.lab@example.net from this PC): one onboarded domain for the whole fleet, the machine in the subaddress, signed with DKIM for example.net; and mail for root and ops goes to the fleet's mailbox (mail in fleets/<fleet>/fleet.ts, here fleet@example.net). It needs the Workers Paid plan, which includes 3,000 messages a month.

In the Cloudflare dashboard, once, in the account that holds example.net:

  1. Compute > Email Service > Email Sending > Onboard Domain: example.net (mail.domain), then Done. Cloudflare adds its records itself: MX, SPF, and DKIM on cf-bounce.example.net, DMARC (p=reject) on _dmarc.example.net; Email Sending > Settings shows each one. New servers need nothing more. DMARC p=reject applies to everything that claims to be from example.net: anything else that sends as example.net must pass SPF or DKIM too.
  2. Create an API token with the permission Account, Email Sending, Edit for this account: either an account token (Manage Account > Account API Tokens, cfat_..., recommended because it outlives any one person's login) or a user token (My Profile > API Tokens, cfut_...). Name it archon mail. Cloudflare shows it once.

On this PC:

bun run stolos boot mail-setup           # paste the token (hidden); then this PC mails its check results
bun run stolos boot mail-push alpha     # give a running server the token; it mails its check results
bun run stolos boot doctor --send        # check again, and mail the email findings

The token is stored in this PC's secrets folder (mail.json), never in git; servers get it at their next install (and mail their check results from the first boot), or now with mail-push, and keep it in /etc/postfix/sasl_passwd (root only). Anyone holding it can send mail as the onboarded domain. To revoke it: Manage Account > Account API Tokens, archon mail, Delete; then create a new one, mail-setup, and mail-push each server. bun run stolos boot doctor and archon doctor check the domain's records, the token, and (on servers) Postfix.

Run the boot server

cd C:\archon
git pull
bun run stolos boot serve

Leave it running while hosts install. It:

  • downloads Ubuntu 26.04's signed boot files and installer image from releases.ubuntu.com once, checks each against the SHA-256 pinned in src/archon-boot/pins.ts (nothing is served on a mismatch), and caches them under %LOCALAPPDATA%\stolos\boot;
  • serves TFTP (PXE) on UDP 69 and HTTP on TCP 8080;
  • shows every machine that boots from it and each install's progress, ending with alpha: ✓ Ready: ...;
  • writes the same lines to %LOCALAPPDATA%\stolos\boot\boot.log (send that file when asking for help);
  • warns, with the command to run, when this PC's firewall would block servers.

Options:

OptionWhen
--address 10.0.1.157this PC has several adapters (WSL, Hyper-V, VPN) and the wrong address shows
--proxy http://proxy:3128the site reaches the internet through a proxy (installer and first boot use it, with Ubuntu's HTTPS mirrors)
--ca-file proxy-ca.pemthat proxy inspects TLS
--port 8080, --tftp-port 69, --no-tftpother ports, or HTTP Boot only

The boot server's own telemetry

The boot server records itself with OpenTelemetry, in its own process, and keeps it on this PC only (spec 023): %LOCALAPPDATA%\stolos\boot\telemetry\boot.otlp.jsonl (its traces and metrics, 256 MB at most) and otlp-<date>.jsonl (what its window shows), in OpenTelemetry's own file format. Each install is one trace, with a span per step.

bun run stolos boot observe          # recent installs: each step and how long it took, what failed
bun run stolos boot observe --last 20

To watch it live, run otel-tui on this PC while boot serve runs; the boot server hands it everything it records. This PC itself is not observed.

Back up the secrets (specs 029 and 056)

This PC holds the only copies of the fleet's secrets: the admin password hash, each host's deploy key and SSH host keys, the Cloudflare DNS token, and the mail token. A backup is one ZIP file that you keep somewhere safe (constitution Article 13):

bun run stolos vault status     # every secret: changed when, backed up when (⚠ = not backed up)
bun run stolos vault backup     # writes the ZIP, reads it back, and says where it is
bun run stolos vault restore <zip>   # a fresh PC: put the ZIP back (checks it; never overwrites)
bun run stolos vault list       # the ZIPs not yet moved out of the backup folder

flowchart LR
  s["every fleet's secrets"] --> z["stolos-backup-‹pc›-‹time›.zip<br/>in stolos's backup folder"]
  k["your signing key<br/>(both halves)"] --> z

vault backup writes stolos-backup-<pc>-<time>.zip into stolos's backup folder (%LOCALAPPDATA%\stolos\backup; Linux and macOS: ~/.local/share/stolos/backup), readable by you only. It holds:

  • secrets/<fleet>/...: every fleet's secrets on this PC, as they are (not the install tokens, which are made again when needed);
  • signing/...: your daily signing key, both halves, from git config user.signingkey (the private half is still locked by its passphrase, which is not in the ZIP);
  • signing/recovery/...: your recovery key, from the key store (%APPDATA%\stolos\keys; Linux and macOS: ~/.config/stolos/keys), locked by its own passphrase;
  • manifest.json: every file's name, size, and SHA-256 (never a value);
  • RESTORE.txt: the restore steps, the same as vault restore (without a ZIP) prints.

It reads the ZIP back and checks every file before saying it worked. Then move it wherever you keep important things safe, for example your OneDrive Personal Vault, a password manager, or an encrypted USB drive, and keep an older one too. One ZIP is everything a disaster needs: every secret and both signing keys. It is not encrypted itself, and with it and your passphrases anyone could change your servers: treat it like the keys to them.

To restore (spec 061), clone the fleet repository on the new PC, cd into it, and run bun run stolos vault restore <zip>. It checks the ZIP (every file against its SHA-256) before writing anything, puts each file back (the secrets readable by you only, the daily key in .ssh, the recovery key in the key store), and runs keys setup, which asks for your daily passphrase once for a test signature. It never overwrites: a file already there and different stops it, naming the file. Run it again and nothing changes. To restore clean instead (exactly the backup, nothing else), add --destroy-existing: it removes every fleet's secrets, the key store, and the daily key first, after saving anything the backup lacks as a ZIP of its own (a different daily key is moved aside as fleet-signing.replaced-<date>; no other .ssh file is touched). See disaster recovery.

Until a changed secret is backed up, Archon says so: a panel at the end of the command that changed it and at the start of boot serve and boot status, a warning in boot doctor, a reminder before each git push, 🔐 backup in the prompt, and an email after a day (then weekly). If this PC is lost, see disaster recovery.

To show 🔐 backup in PowerShell with oh-my-posh and this theme, add to your profile:

function Set-ArchonStatus { $env:ARCHON_STATUS = (Get-Content "$env:LOCALAPPDATA\archon\status\prompt-vault" -ErrorAction SilentlyContinue) }
New-Alias -Name 'Set-PoshContext' -Value 'Set-ArchonStatus' -Scope Global -Force

The network reference (spec 028)

The UniFi network is modeled in fleets/<fleet>/site.ts: networks, zones and policies, DNS, the mDNS proxy, Wi-Fi, WireGuard, the boot server, and fixed addresses (names only, never passwords). The router is the authority (constitution Article 21): change UniFi first, then the model to match. stolos build checks it (for example that a network booting from this PC has its two policies) and renders the reference, out/site/network-reference.html. To send a network change log to the shared mailbox:

bun run stolos build
bun run stolos boot notify --subject "Lab Network Runbook Change Log 2026-11-12" --body-file changes.txt --attach out\site\network-reference.html

If this PC's address changes, set site.bootServer.address: stolos build then lists every UniFi setting that still points at the old one.

Check the boot machine

bun run stolos boot doctor

Read-only. It checks the checkout (uncommitted or unpushed host changes, which hosts would not see), the model, the secrets, Ubuntu's files, the network address, the ports, the firewall, and email (the sending domain's records, and whether Cloudflare accepts the token; nothing is sent), and prints the fix for each problem.
