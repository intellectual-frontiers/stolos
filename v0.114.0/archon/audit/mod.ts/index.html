The auditor portal

An external auditor tests a control by sampling its population and examining each sample's evidence. Stolos gives them both from the signed evidence bundle (spec 072), so they verify each sample themselves and never need a screenshot (spec 083).

flowchart LR
  open["stolos audit open: engagement.ts (signed commit)"] --> pin["stolos audit bundle: the period's evidence bundle"]
  pin --> pop["populations: a typed query per control over the bundle's items"]
  pop --> sample["stolos audit sample: the auditor's seed, a published method"]
  sample --> trail["the trail: requests, responses, samples (signed commits)"]
  trail --> portal["the portal: /audit/&lt;id&gt;/ on 127.0.0.1, time-boxed"]
  trail --> export["stolos audit export: a package to verify offline"]

1. Open an engagement

deno task stolos audit open soc2-2026 --firm "Example CPA" --auditor "Dana Example <dana@example.com>" \
  --from 2026-01-01 --to 2026-06-30 --framework soc2 --expires 2026-09-30 \
  --controls "CC6.2=leavers,CC6.1=mfa,CC8.1=change,CC6.3=access-reviews"
deno task stolos evidence export --from 2026-01-01 --to 2026-06-30
deno task stolos audit bundle soc2-2026 <the bundle's path>

The engagement is fleets/<fleet>/audits/<id>/engagement.ts: the firm and its people, the period, the frameworks, the controls in scope (each with the population it is tested on), the evidence bundle (pinned by its SHA-256), and the last day of the auditor's access. Each audit command makes one commit of the engagement's files, signed with your daily key; push it as any change (stolos apply). audit access moves the last day; audit close ends the engagement.

2. Populations

Each control is tested on a population computed from the pinned bundle, never from this PC's live state, so the auditor gets the same units and the same population hash from the bundle alone:

Population One unit is
change a commit to the fleet repository in the period
leavers a person whose employment ended in the period
mfa an active account (not a service account)
devices a device, or a machine Stolos adopted
repositories a code repository
access-reviews a manager's quarterly access review
verify a managed server's verify or install result

Each unit names the bundle items that are its evidence, by SHA-256.

3. Samples

The auditor chooses the sample size (by their firm's methodology) and gives a seed: any text, such as a number they picked or a public randomness beacon's value they chose. Stolos draws by simple random sampling without replacement with random sort keys (each unit's key is sha256(seed + newline + unit id); the sample is the units with the smallest keys), so the auditor redraws it with a shell:

deno task stolos audit sample soc2-2026 --control CC6.2 --seed 734019 --size 5

The sample, the seed, the method, and the population's hash are recorded in the trail.

4. Requests and responses

deno task stolos audit request soc2-2026 --by "Dana Example" --control CC6.2 --text "For each sampled leaver: ..."
deno task stolos audit respond soc2-2026 --re 3 --text "Each sample's evidence is on its page ..."

Each is a numbered file in audits/<id>/trail/, added in a signed commit whose trailer names the file's SHA-256: the signature covers the exact text. The portal shows them in order, each with its commit and signer.

5. The portal

deno task stolos audit portal soc2-2026

It starts the Stolos Console on 127.0.0.1 and prints a link that works once, for two minutes, and opens a session that sees only this engagement, read-only, for at most four hours. Every page refuses once the engagement has expired or been closed. The auditor sees each control's population, each sample's evidence items with their SHA-256 and place in the signed manifest, and verifyBundle's result, and downloads any item or the whole bundle. The same data is JSON under /v1/audit/<id>/ (in the console's OpenAPI document).

6. A remote auditor: the export package

The console answers only on this PC. For an auditor elsewhere, send the export package:

deno task stolos audit export soc2-2026
deno task stolos audit verify lab-audit-soc2-2026.zip   # the auditor, offline

It holds the bundle, engagement.ts and every trail entry with the raw signed commit that recorded it, the populations, the fleet's signers, and the portal as one static page. audit verify checks the bundle, every commit's trailer and signature, and recomputes every population and redraws every sample; its README says how to do the same by hand. The package is not time-boxed: sending it is your decision.

Interfaces

I
Auditor

One person at the audit firm.

  • email: string

    Their work email, when given.

  • name: string

    Their name.

I
Engagement

An audit engagement: fleets/<fleet>/audits/<id>/engagement.ts.

  • access: { expires: string; }

    The portal's time box: it refuses every request after this day (YYYY-MM-DD, UTC, the day included).

  • auditors: Auditor[]

    The firm's people who may see it.

  • bundle: PinnedBundle

    The evidence bundle, once pinned.

  • closed: { on: string; by: string; }

    When it was closed (YYYY-MM-DD), and by whom; the portal refuses a closed engagement.

  • controls: ScopedControl[]

    The controls in scope.

  • firm: string

    The audit firm.

  • frameworks: string[]

    The frameworks in scope (soc2, iso27001, hipaa, pci, ...).

  • id: string

    Its id: the folder's name (lowercase letters, digits, dashes).

  • opened: { on: string; by: string; }

    When it was opened (YYYY-MM-DD), and by which fleet signer.

  • period: { from: string; to: string; }

    The period audited (YYYY-MM-DD, both days included).

  • title: string

    Its name for people ("SOC 2 Type 2, 2026").

I
PinnedBundle

The evidence bundle (spec 072) an engagement's populations are drawn from.

  • file: string

    Its file name in this PC's evidence directory.

  • head: string

    Its manifest's head (the end of its hash chain).

  • sha256: string

    Its SHA-256: a different file with that name is refused.

I
SampleRecord

A sample, as the trail records it.

  • control: string

    The control in scope it tests.

  • method: string

    SAMPLE_METHOD.

  • population: PopulationId

    The population it is drawn from.

  • populationHash: string

    The population's hash when it was drawn.

  • populationSize: number

    How many units the population had.

  • seed: string

    The auditor's seed.

  • size: number

    The size asked for.

  • units: string[]

    The units drawn, by id, in draw order.

I
ScopedControl

One control in scope, and the population it is tested on.

  • framework: string

    The framework it is from (soc2, iso27001, ...), when it is one framework's.

  • id: string

    The control's id as the auditor names it (a criterion such as "CC6.2", or the company's own id).

  • population: PopulationId

    The population it is tested on (a typed query over the bundle's items).

  • scf: string[]

    The SCF controls it maps to, when known.

  • title: string

    What it is, in words.

I
TrailEntry

One entry of the trail.

  • at: string

    When it was recorded (ISO time).

  • body: string

    Its text (Markdown).

  • by: string

    Who made it: the auditor for a request, the company's person for a response.

  • control: string

    The control it is about, when it is about one.

  • kind: EntryKind

    What it is.

  • re: number

    The request a response answers (its seq).

  • sample: SampleRecord

    The sample, for a sample entry.

  • seq: number

    Its number: entries are shown in this order.
