pair-store

Specs 103-three-ports and 107-pairing-and-query: where a pairing session's state lives. A session (spec 098) has one record: the code, the fleet, the wrong signatures counted per client address, and every machine that said hello, with its check-in waiting for the person and the person's decision for it. stolos pair (the terminal, where the person approves) and every server that answers a machine (the boot server, the console, or the pair-only server stolos pair runs itself) are different processes, so the record is a store they share:

  • MemoryPairStore: one process (the tests, and a session with no other process);
  • FilePairStore: a short-lived file in the secrets folder, owner only and ephemeral (never backed up), the same pattern as an armed install: the command writes, the servers read per request, and there is no new port. Every change is made under a lock file (<file>-lock, taken with O_EXCL by commons' lock), read fresh inside it, and written atomically (a temporary file renamed over the record), so two processes cannot lose each other's tries or machines.

The record has no expiry: a session lasts until the person who started it stops it (spec 107-pairing-and-query FR-001). It is bounded instead: at most MAX_ADDRESSES client addresses are counted and at most MAX_MACHINES machines are kept, so a flood cannot grow the file without limit (FR-004).

Source: src/archon/adopt/pair-store.ts

MAX_TRIESconst
const MAX_TRIES: 5

How many wrong signatures one client address may send before it is refused for the rest of the session.

MAX_ADDRESSESconst
const MAX_ADDRESSES: 256

How many client addresses a session counts wrong signatures for (past it, a new address's wrong signature is refused uncounted).

MAX_MACHINESconst
const MAX_MACHINES: 64

How many machines one session keeps (a hello from another is refused).
