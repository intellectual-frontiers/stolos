The fleet repository

#The fleet repository: pin, lock, upgrade

This guide is for whoever looks after a fleet repository (for example example-org/fleet): the private repository that holds your fleets and that every host checks out at /srv/archon. Read it once before your first engine upgrade; keep it at hand for the troubleshooting table at the end.

#What is in a fleet repository

Nothing here is the engine itself. The engine lives in the public repository intellectual-frontiers/stolos; each version is a tag of it (v<version>), and bun install puts the engine at that tag in node_modules/, as its TypeScript sources. There is no GitHub release and nothing to build: Bun runs the sources, and Node 26 runs them with commons' hook (node --import @intellectual-frontiers/commons/ts/node stolos.ts).

#Starting a new fleet repository

You need Bun, git, and gh signed in (gh auth login). Create an empty private repository on GitHub, clone it, and from inside the clone run the engine once at a version tag (replace <version> with the newest tag of intellectual-frontiers/stolos):

fleet init lab writes package.json pinned to that same tag (the commands stolos and archon), stolos.ts, archon.ts and .gitignore, runs bun install (which writes bun.lock), then fleets/lab/fleet.ts from your GitHub identity. It asks for your Unix account name and an admin password; only the password's hash is kept, on your machine, never in Git. From then on use the pinned engine through the tasks:

A second fleet in the same repository is one more bun run stolos fleet init <id>. When the repository holds more than one fleet, choose the one this checkout works on, once: bun run stolos fleet use lab (remembered in .git, never committed; fleet init chooses the fleet it creates). For one command, --fleet <id> (or ARCHON_FLEET) chooses another, for example bun run stolos boot serve --fleet lab. Files that already exist are never overwritten by fleet init.

#Why the pin and the lock matter (security, not only tidiness)

Every host runs archon as root, so whatever code it runs can do anything on that host. That code comes from two places:

  1. This repository. A host only moves to a commit at the tip of main that is signed by one of the fleet's signers (fleets/<id>/signers.ts, stolos signers). Pushing an unsigned commit does nothing: every host refuses it and says so in its journal.
  2. The engine. It is downloaded from GitHub, the engine's repository at its tag (github:intellectual-frontiers/stolos#<tag>). Your signature does not reach the engine by itself: it is not in this repository.

bun.lock is what joins the two. It is a file in this repository, so it is covered by your signature, and it holds the commit the tag named and the integrity of that commit's archive. Hosts install the engine with bun install --frozen-lockfile: they fetch that commit, not whatever the tag names today, and if what they download differs from the lock (a moved tag, a compromised GitHub account, an altered file on the way), Bun refuses to install it. The host stays on the commit it runs; it does not run unapproved code.

So: never drop --frozen-lockfile, never hand-edit bun.lock, and never change the pin without stolos fleet upgrade. If something about the lock is in your way, the table at the end says what it means and what to do.

#The pin

package.json holds one dependency:

v0.8.0 is the engine version. Engine versions only go up (0.7.0, 0.8.0, 0.9.0, ...); each one is a tag that the engine's CI made after its checks passed (and after installing that commit as you do, and running it on Bun and on Node). The tag is the release: there is nothing else to download. The installed package's own package.json says the same version: that is how fleet upgrade knows a tag is a real version.

#The synthetic fleet: test before a real server

A fleet repository can hold a synthetic fleet: a fleet made for the end-to-end lab, shaped like your real one (the same providers, mail and web settings, capabilities), with made-up hosts. GitHub Actions installs its server from a blank Secure Boot VM with the engine your package.json pins, reboots it, and sets up its workstation, which then reaches the server over MCP. When that passes, the same engine version and the same kind of model are ready for a physical server.

Each run makes its own signer, admin password hash, and the server's host keys, signs the fleet's tip, and throws all of them away: nothing secret is stored in the repository or in GitHub. Use providers: { acme: "letsencrypt-staging" } and documentation domains (example.net) so nothing reaches a real provider.

The workflow in the fleet repository calls the engine's, at the same tag as the pin (archon fleet upgrade moves both):

How the server is installed in the lab. A private repository's runners have 8 GB of memory, too little for Ubuntu's network installer (it holds the whole installer image in memory) next to the runner itself. There, the lab starts the server from Ubuntu's cloud image and finishes it with stolos host bootstrap, the path for a server installed by hand: the same first boot, fleet, signers, and registered SSH host keys. The engine's own lab (public, 16 GB runners) runs the full network install, Secure Boot and all, on every engine release.

Cost. A run in a private repository takes about 8 minutes of a Linux runner, counted against the GitHub account's included Actions minutes (2,000 a month on the Free plan, 3,000 on Pro); beyond them, GitHub charges only if you set a budget above zero. Run it by hand, for difficult or major changes (install, identity, boot); simple ones are proven in the engine's public lab and then on the real machines. Check usage under Settings, Billing and licensing.

#Registration: who each host is

stolos host add <host> writes fleets/<id>/hosts/<host>/registration.ts: the host's SSH host public keys (the private halves stay on the boot machine and in its backup ZIP), its network card, and its deploy key's fingerprint. Commit it with the host's host.ts.

Your machine checks every server against those keys, so a first connection is never trusted blindly: stolos fleet status and stolos fleet query do it on their own, and once on each workstation (and again after a host is added) run

so plain ssh <host> and your MCP client check the same keys. If ssh ever says a host's key changed, do not accept it: compare with registration.ts, and ask whoever looks after the boot machine.

#Decisions: what is on, on each host

Opt-ins (PostgreSQL, S3, SMB shares, the telemetry web UI) are off on every server until someone turns one on. Record that decision in Git, from your workstation, so it is approved like any other change and survives a re-install:

It writes fleets/<id>/hosts/<host>/decisions.ts; the host applies it within 15 minutes. A decision in Git wins over anything recorded on the host itself. Durable or ephemeral matters: durable data is backed up, and the boot machine refuses to re-install a durable host unless a person types --confirm-destroy <host> (Article 23); going from durable to ephemeral needs the same.

Running archon pg on (and the others) on the host itself still works, but only that machine remembers it; it tells you the stolos decide line that records it in Git.

#Signing: your keys (spec 057)

Each operator signs with their own key, listed in the fleet's signers.ts. The key is a file, protected by a passphrase that you type and never store; it is never loaded into an ssh-agent, so nothing on your machine (an agent included) can sign without you. One command sets it all up, and can be run again at any time (it does only what is missing, and never overwrites a key):

keys setup makes your daily key (~/.ssh/fleet-signing) and a recovery key in this PC's key store (%APPDATA%\stolos\keys; Linux and macOS: ~/.config/stolos/keys), each locked by its own passphrase. Every backup (bun run stolos vault backup) holds both keys with every secret, so one ZIP is everything a disaster needs: keep it somewhere safe and encrypted, since with it and your passphrases anyone could change your servers. Prove the recovery key still works twice a year (stolos keys reminds you):

The pre-push check keys setup installs refuses, on your PC, a push that servers would refuse (an unsigned commit, or one signed by a key signers.ts does not list), with the fix.

#Modules

applySpec 060: stolos apply (or stolos push): your changes to the fleet, from this PC to every machine, in one command and at most one passphrase.
bootstrapSpec 062: the bootstrap scripts that make a PC a Stolos controller (the pinned Bun, Git, gh, the GitHub sign-in, the fleet cloned into $HOME/fleet, the stolos shortcut).
decisionsSpec 047-intent-and-identity (Article 25): what operators decided for a host (which opt-ins are on, and whether their data is durable) lives in Git, in fleets/<id>/hosts/<host>/decisions.ts, written…
recordsSpec 099 (FR-006): the files in a fleet repository that Stolos writes itself, as records of what happened (an install's registration, an adoption, an observation).
registrationSpec 047-intent-and-identity (Article 25): who a host is, in Git: fleets/<id>/hosts/<host>/registration.ts, written by stolos host add, in one fixed form.
releasesSpec 099: the newest Stolos release, as stolos update, the Stolos Console and the Archon Console show it.
scaffoldA new fleet repository's files (spec 046-engine-instance): what archon fleet init <id> writes into a repository that has none of them yet.
signingSigning a commit with the person's daily key, and what is said about it (spec 105-calm-output FR-012, FR-013, FR-014): the line that names what is being signed, a wrong passphrase retried in place…
upgradestolos fleet upgrade <tag> (spec 046-engine-instance, Articles 9, 12, 24; spec 096 FR-006): move a fleet repository to another version of the engine, safely.
usestolos fleet use <id>: which fleet of this repository every archon command in this checkout is for, remembered in .git/stolos/fleet (never committed, so each checkout chooses its own).
whatsnewWhat's new after an engine upgrade (spec 105-calm-output FR-016): up to five bullets from the engine repository's commit subjects between the old and the new tag, from GitHub's public compare API…
