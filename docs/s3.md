# S3 object storage

Every server can serve S3-compatible object storage (RustFS). It is an **opt-in container**: present
on every server and off until an operator turns it on; then it stays on, across reboots and
reinstalls, until an operator turns it off (specs 040, 041). `archon opt-in` lists every opt-in
service and container.

## Turn it on (an operator, once per server)

```sh
archon fs s3 on --durable   # or --ephemeral: there is no default
```

`--durable` or `--ephemeral` is required, with no default (constitution Article 23, spec 044):
**durable** when what is in its buckets (`/srv/s3`) exists nowhere else (it is archived nightly, and
nothing reinstalls or wipes this server without `--confirm-destroy`, typed by a person);
**ephemeral** when losing it is harmless. `archon data` shows the server's class and why;
`archon data set` changes a choice later.

RustFS starts under Podman (pinned by digest, as an unprivileged user with every capability dropped,
on the server's loopback only), and Traefik serves it (the router decides who reaches it):

| What            | Address                                                                        |
| --------------- | ------------------------------------------------------------------------------ |
| The S3 API      | `https://s3.<server>.<domain>` (for alpha, `https://s3.alpha.lab.example.net`) |
| The web console | `https://s3-console.<server>.<domain>`                                         |

`archon fs s3 status` shows whether it is on and ready. `archon fs s3 off` stops it and keeps it
stopped; buckets, users, and keys are kept.

## Your S3 user is your Linux account

Every person on the server, and every fleet service account (`s-<app>`), has an S3 user of the same
name. You may use the buckets whose names start with your name and a dash (`alice-photos`,
`s-app1-uploads`), and no others.

S3 signs every request with a secret the server keeps, so it cannot be your Linux password. Archon
generates your secret on the server, and only you (and root) can read it:

```sh
archon fs s3 key            # your access key (your username), the endpoint, your buckets
archon fs s3 key --write    # the profile s3-<server> in ~/.aws/credentials and ~/.aws/config
```

`--write` changes only that profile in those two files (both readable by you only). An app gets its
key the same way, as its own account: `sudo -u s-app1 archon fs s3 key --write`.

## Connect

With the `aws` CLI:

```sh
aws --profile s3-alpha s3 mb s3://alice-photos
aws --profile s3-alpha s3 cp picture.jpg s3://alice-photos/
aws --profile s3-alpha s3 ls s3://alice-photos/
```

With `rclone` (`rclone config`, type `s3`, provider `Other`): the endpoint
`https://s3.alpha.lab.example.net`, your access key and secret, `force_path_style = true`.

With an SDK: the endpoint above, region `us-east-1`, path-style addressing (for example
`forcePathStyle: true` in the AWS SDK for JavaScript, `addressing_style: "path"` in boto3). Buckets
are paths (`https://s3.<server>.<domain>/<bucket>/<key>`), not host names.

### The web console

The console (`https://s3-console.<server>.<domain>`) asks for an **Account** and a **Key**. They are
not your Linux username and password: S3 signs every request with a secret the server keeps, so it
cannot use your Linux password.

- **Account**: your Linux username (for example `alice`).
- **Key**: your S3 secret. Print it on your own terminal with `archon fs s3 key --show` and paste it
  in. It is never shown in JSON, written to a log, or given to an agent.

"Login Failed" with your Linux password is expected; use the secret.

### A new secret

If your secret may have been seen (pasted into a chat, shown on a shared screen), replace it:

```sh
archon fs s3 key --rotate   # asks sudo; the old secret stops working at once
archon fs s3 key --write    # update ~/.aws
```

Then update anything else that uses it (apps, rclone) and sign in to the console again with
`archon fs s3 key --show`. Only the fact that it changed is recorded (`journalctl -t archon-s3`),
never the secret.

## Good to know

- The data is in `/srv/s3` on the server. It is in the nightly backups when S3 was turned on
  `--durable` (constitution Article 23), and not when `--ephemeral`; the credentials and keys always
  are.
- Bucket names are lowercase letters, digits, dots, and dashes: an account whose name has another
  character cannot name a bucket after itself.
