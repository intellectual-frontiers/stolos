# Implementation Plan: Integrations: one typed layer over routers, DNS and email, and UniFi as the first router

**Branch**: `109-integrations-api` (committed directly to main) | **Date**: 2026-11-17 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/109-integrations-api/spec.md`

## Summary

The ontology says what kinds of API there are and what each kind can do (`stolos:ApiKind`, `stolos:ApiCapability`). A small algebra
(`src/archon/connect/integration.ts`) turns those words into types: an integration is declared with its kind and the capabilities it
offers, a function that needs a capability takes `Has<kind, capability>`, and the compiler refuses the rest. Each capability's result
is a typed entity (`integration-entities.ts`), which `integrationConnector` writes into a spec 084 observation as records and device
entities, so the estate graph (085, 090) is the one graph. Cloudflare is given the `dns` and `email` kinds without changing its
connector. UniFi Network is the first `router`: its types are generated by `tools/unifi-api-gen.ts` from the pinned official
OpenAPI document (10.3.58, `vendor/unifi-network/`), its client is TypeScript over the runtime's `http`, and its TLS is a pinned
fingerprint or an explicit CA, never switched off.

## Design notes

- **The kinds and capabilities are one fact.** `API_CAPABILITIES` (the ontology's union, generated) holds `<kind>-<capability>`; the
  type `CapabilityOf<K>` picks the capabilities of a kind by a template literal type; `Results` maps each to its entity list and a
  compile-time assertion (`Same<keyof Results[K], CapabilityOf<K>>`) fails where the two differ.
- **`Has<K, C>` is structural**, so a function over a capability never names an integration, and an integration that offers more
  is accepted. `defineIntegration` infers the offered set from the keys of `read` and demands `notOffered` for exactly the others.
- **One observation, many labels.** An integration's entities become `ObservedRecord`s (a label from OCSF or D3FEND and its OCSF class) and,
  for adopted devices, `Entities.devices`. The connector framework's `toEntities` and the estate graph do the rest.
- **Reads are guarded and bounded.** Each capability is read inside `orGap`: a denied call (401, 403) or an endpoint the version does
  not have (404) is a gap; a network or TLS failure is not (the account was not reached). Paging is capped (50 pages, 100 sites, 500
  devices for the port reads), every request has a time limit.
- **The TLS code is a socket, then a request.** `unifi-tls.ts` connects with `node:tls`, verifies (pin: exact SHA-256 of the leaf;
  CA: Node's full verification; neither: the system's roots), and only then writes an HTTP/1.1 request with `Connection: close` and
  reads the answer (content length, chunked, or until close). It is exposed as a `fetch` for the runtime's `liveTransport`, so the
  guard, the backoff and the credential policy of spec 089 still apply. The probe that shows a certificate to the person sends
  nothing: it reads the certificate and closes.
- **Cloudflare is wrapped, not rewritten.** `withIntegrations(cloudflare, ...)` keeps `cloudflare.ts` as it is; the wrapper runs the
  integrations' reads on a `memoGets` transport after the connector's own, adds records, posture facts, gaps and the email
  policies, and leaves every field the connector wrote as it was. The web front door's Cloudflare code (spec 032) is not touched
  (`tasks.md`, L001).
- **The generator is small because the document is.** It uses `allOf`, `discriminator`, `additionalProperties`, `enum`, `items`, `$ref` and
  formats; it fails on any other keyword, so a new document that uses more is a decision, not a silent loss.

## Standards considered

The same ones as the specification (`spec.md`, Standards considered): RFC 2119 and RFC 8174 for the requirement words; the OpenAPI
Specification 3.1.0 for the pinned document and its generator; RFC 9110, RFC 8259, RFC 5280, RFC 6125 and RFC 8446 for the API, its JSON
and its TLS; RFC 1034, RFC 1035, RFC 7208, RFC 6376 and RFC 7489 for DNS and the email DNS records; RFC 2131 and RFC 8415 (DHCP) and
IEEE 802.1Q (VLANs) for the router entities; OCSF 1.9.0 and MITRE D3FEND for the labels; NIST SP 800-53 Rev 5 (CM-8, SC-7, SC-8,
SC-20), SP 800-41, SP 800-153 and SP 800-177 for the posture policies, with the SCF controls AST-04, MON-02, VPM-08, NET-24, NET-10,
CRY-05, CRY-09 and NET-39; W3C SKOS and schema.org `WebAPI` for the two code lists and the integration (`ontology/stolos/audit.ts` maps
them and the OCSF and D3FEND terms). The six terms no standard names (a lease, a port forward, a route, a Wi-Fi network, a router's
health, an email sender) are `unaligned` in the audit with what was examined, and are the only lines this change adds to
`tools/mizan.baseline.txt`.
