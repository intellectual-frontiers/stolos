unifi-tls

Spec 109-integrations-api FR-012: how a connector trusts a controller whose certificate no public authority signed (a UniFi controller's own, usually). TLS verification is never switched off: a connection is made only to a server that is

  • pinned: its leaf certificate has exactly the SHA-256 fingerprint the person approved (the chain is not checked: a self-signed certificate has none; the exact certificate is the trust, which is stronger than a chain), or
  • in a CA set: its certificate verifies against the CA certificates given in the connector's settings, host name included (Node's own verification, ca), or
  • public: where neither is given, it verifies against the system's roots.

The check is made on the TLS socket before any byte of the request is written, so the API key never reaches a server that is not the trusted one. fetch takes no per-host certificate options on both runtimes, so the request is written here, over that socket (HTTP/1.1, Connection: close, no compression), and the answer is read to its end; the result is a fetch for the runtime's liveTransport, so the guard, the backoff and the credential policy of spec 089 still apply to it.

probeCertificate is what stolos connect uses to show a certificate to a person (trust on first use, as SSH host keys): it reads the certificate and closes, and sends nothing.

Source: src/archon/connect/unifi-tls.ts
